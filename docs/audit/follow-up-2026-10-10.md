## Confirmed source findings

### October 11 implementation progress

Canonical partner intake now has private applications, consent, operator feedback/rejection, applicant correction/resubmission/withdrawal, replay and revision controls, active-type duplicate prevention, export and deletion integration. Private document intake, actual Storage quarantine orchestration, quotas, retention/removal, mutual-TLS ClamAV scan worker, integrity-bound clean downloads and phone/web save/share source are also implemented. Local tests use storage/scanner fixtures; real bucket IAM/rules, scanner/certificates, identity/business verification, review/activation, historical migration and physical devices remain unaccepted. No onboarding checklist item is marked complete on this evidence alone. Configuration/acceptance details are in release/partner-documents.md and implementation-2026-10-11.md.

Operations now has an audited, replay-safe merchant business draft creation command and form, with validated identity/name/address/time zone and protection against overwriting existing stores. Drafts remain closed even if acceptingOrders is changed and are excluded from customer discovery. No merchant access or compliance approval is implied by creation. Existing role provisioning can assign an actual created catalog after operator review. Canonical application intake, private KYB documents, review/activation, owner consent and full merchant onboarding remain open.

Merchant closure calendars now support up to 90 validated store-local dates, including blocking overnight spill from a closed previous day. Business-scoped commands use closure revisions, immutable history and retry-safe request IDs; the merchant editor detects concurrent changes and offers explicit reload/discard. Checkout and catalog search use the shared availability policy. Direct privileged store/catalog writes are denied by rules, and legacy availability/stock helpers now call validated audited server commands. Scheduled pickup slots, workload capacity, public closure messaging and full staging acceptance remain open.

Grocery preparation now has a scoped picking command, packed-quantity editor, revision conflicts, immutable replay-safe history and a readiness guard requiring exact full quantities for every reserved order line. Customer tracking reports picking progress. Picking does not alter stock reservations or charged prices. Substitutions, partial fulfillment/refunds, actual weighted-item billing, expiry/barcode workflows and real staging acceptance remain open.

The captured-payment/out-of-stock refund path now remains unresolved until verified provider payment evidence posts the cumulative refund journal. It no longer exits the worker queue based only on the create-refund response. A regression checks zero booking creation, no wallet debit, one refund request and the confirmed journal. Webhook failure logs now emit bounded error codes rather than raw exception objects. Historical refund journal backfill, provider acceptance and full finance reconciliation remain open.

Account export now includes private support replies/history, booking events, driver jobs/earnings/payouts and allowlisted payment fields. Linked Neon account-store history is included separately; SQL booking export now reads the actual ownership-scoped booking table. Canonical IDs override embedded data IDs for pagination. Driver support retries reuse an idempotent case reference and drivers have a data-export entry point. Full native export usability, large-account server jobs and a live cross-store export acceptance journey remain open.

Deletion now redacts booking exception/preparation free text and event reasons for the deleting customer's records, while preserving amounts, workflow stages and revisions. Driver-authored event reasons are redacted during driver deletion. Real dual-store lifecycle acceptance, approved retention rules and historical migration still remain open.

Dispatch timeout recovery now has operator-configured service thresholds, versioned policy history, a rotating scheduled scan, transactional assignment rechecks and an idempotent no_partner exception. Merchant readiness and driver release record the search start; operations resolution resets it. Deployment, legacy readiness migration, high-volume latency, pickup timeouts, direct dispatch management and live reassignment acceptance remain open.

Unaccepted merchant orders now have a reasoned rejection command with current business authorization, immutable rejection history and full wallet/provider refund orchestration. Prepared or assigned orders remain operations-controlled. Service cancellation policies, partial fulfillment and live refund acceptance remain open.

Booking exceptions now have participant-scoped reporting, immutable report/resolution events, command replay protection and revision-checked operations resolution. Open problems pause merchant fulfillment, driver progression, assignment and job release while retaining the assigned driver's custody. Customer tracking, merchant/driver screens and the operations review panel expose the problem and resolution. Physical handling procedures, return journeys, damage evidence, dispatch timeout escalation and compensation remain open; this is not full failure/return acceptance.

Refund recovery now has a paginated operations queue and a scheduled provider-evidence worker with a rotating cursor. It does not initiate new refunds. Provider cancellations persist the refund state on both booking and payment before the provider call; refund confirmation uses the canonical payment evidence and journal reconciliation. Real Razorpay/bank acceptance remains open. The idempotent request uses Razorpay's documented X-Refund-Idempotency contract: https://github.com/razorpay/markdown-docs/blob/master/api/refunds/normal-refunds-idempotent.md.

Wallet top-ups now persist an owner-bound funding intent before provider creation, reuse it across concurrent retries and app restarts, and reconcile uncertain creation by its exact provider receipt. The wallet status action releases its local pending reference only after a verified paid or fully refunded result. Live provider and bank acceptance remain open.

Support cases now use server-authorized commands for order association, assignment, replies, escalation, resolution and reopening, with immutable event history and revision checks. Customers and staff have private conversation panels; operations has a paginated queue. New legacy SQL ticket creation is disabled so requests cannot enter an unmanaged second queue. Existing SQL history remains retained and exportable; migration, attachments, notifications, SLA escalation and fine-grained staff authorization remain open.

Verification and password reset email templates now link to the account-action screen with opaque tokens in the URL fragment, cleared from browser history on load. Actual sender verification, public HTTPS hosting and email/device acceptance remain open. See implementation-2026-10-11.md for configuration steps.

Global food/grocery item search now has a server-maintained prefix index, pagination and canonical live checks for current name, stock, price, availability and merchant hours. Existing catalogs need the explicit backfill after deployment. Geographic ranking and coverage-based discovery remain open; checkout still confirms coverage.

Merchant preparation timing now has a scoped server command, bounded 1–240 minute estimates, customer-visible reasons, revision history and idempotent request replay. Restaurant/grocery merchants can publish or revise estimates before readiness; customers see the estimate and an explicit overdue message. Booking notifications now include preparation revisions in their change detection. Real push acceptance, SLA escalation, merchant refusal/refund, grocery substitutions and operational acceptance remain open. This does not complete the entire merchant workflow.

The later pasted review's claims that countdowns, Android background collection and settlement editing are absent are outdated for this working tree. Countdown/expired-button handling, Android foreground location service and versioned settlement editing already exist; their remaining device/provider acceptance requirements still apply. Tipping, referrals and internationalization are additional open feature requests, with no implementation or business policy accepted yet.

# AllGo — Production Architecture, Feature and Security Audit
**Audit date:** 2026-10-09 (Asia/Kolkata)  
**Repository:** https://github.com/logeshn554/delivery123  
**Branch / reviewed tree:** `main`, `489991268ab7164ec05108270aa5cd59025193de`  
**Scope:** Read-only connected GitHub source inspection, repository tree (184 tracked files), relevant implementation files and project documentation. **No changes made; no npm/Gradle/Xcode tests run; no deployed application, secrets, providers, or production databases accessed.**

## Executive determination
**Launch decision: NOT READY for real-money, real-driver or public production operations.** This is not a blank mockup: the repository has real source code for six service categories, Firebase Functions payment/dispatch/settlement, Firestore authorization rules and emulator-based tests, Neon/PostgreSQL account APIs, Android and iOS Capacitor shells, and a number of screens. However, its own `CHECKLIST_STATUS.md` says that staging acceptance is incomplete. Payments, native auth, background location, release signing, business coverage, live data, merchant onboarding, legal policies and end-to-end provider/device evidence are outstanding. A code file is not evidence of a deployed, working service.

**Product definition:** One AllGo platform with customer, driver/fleet partner, merchant, and operator experiences; a shared identity and booking core; service-specific fulfillment logic. The correct first step is NOT to add independent pages, microservices or a second disconnected order table for each vertical.

## 2. Findings by severity — exact paths and scenarios

### P0 — Launch blockers / integration-critical

**P0-01: Two partially overlapping backends require a single authoritative contract.**  
**Files:** `src/accounts.ts`, `src/data/firestoreHelper.ts`, `src/data/neonAccounts.ts`, `server/accounts.mjs`, `server/firebaseIdentity.mjs`, `src/App.tsx`.  
**Evidence:** Neon-mode requests use PostgreSQL API; the client routing helper switches to Firebase only when `hasServiceIdentity` is true. Without a bridge, most Firebase services reject operations. The Neon API exposes account/catalog/booking read endpoints but does not implement Firebase-equivalent checkout, dispatch, refunds and privileged roles. The current `allgo_bookings` SQL table is not evidence of completed Neon fulfillment.  
**Scenario:** A verified customer can see a catalog/profile and then fail at checkout/tracking, or see divergent Neon/Firebase data.  
**Fix:** Make a decision: (A) keep Neon as account authority and Firebase as order authority, formally specify a bridge and canonical UIDs; or (B) consolidate into one principal backend. Recommended near-term: A with explicit mapping tables, lifecycle reconciliation, verified bridge, and only ONE canonical booking and finance ledger. Test signup, login, role promotion, profile edit, logout, expiry, data export, deletion and new booking across both systems.

**P0-02: Production acceptance and provider configurations are absent from evidence.**  
**Files:** `CHECKLIST_STATUS.md`, `PRODUCTION_SETUP.md`, `PAYMENTS.md`, `MAPS_SETUP.md`, `RELEASE_HANDOFF.md`, `.env.staging.example`, `scripts/check-release.mjs`.  
**Evidence:** Status explicitly states no phase has final staging acceptance; separate staging settings, real payment/Maps provider credentials, native registrations and App Check attestation require setup.  
**Scenario:** Deployment compiles but cannot authenticate, quote, pay, track or notify.  
**Fix:** Separate staging/production projects and DBs, configure all third-party services, perform full six-service acceptance in staging before taking real money.

**P0-03: Database and project configuration can drift.**  
**Files:** `firebase.json`, `.firebaserc`, `firebase-applet-config.json`, `src/firebase.ts`, `functions/index.js`, `.env.staging.example`, `scripts/check-release.mjs`.  
**Evidence:** Current default project is `golden-polygon-3rrhs`; checked-in Firestore config targets the named database `ai-studio-33ff364a-171b-472c-93a0-dd18e20cf1e4`, while staging example asks for `(default)`. Firebase client/function code can fall back to the checked-in database. Release checks compare selected environment variables but do not verify the `firebase.json` database selection against the requested release target.  
**Scenario:** Staging app/build may point to a different DB than rules/indexes deployment, or a missing variable silently points a build to the wrong project/DB.  
**Fix:** Explicit per-environment Firebase CLI configs; no production client fallback; deployment assertion compares project, database, Cloud Functions trigger DB, native registrations and app environment; prohibit staging from using production project/DB.

**P0-04: Service identity, payment and booking journey must be tested atomically.**  
**Files:** `server/firebaseIdentity.mjs`, `functions/index.js`, `src/components/CustomerApp.tsx`.  
**Evidence:** A custom-token bridge, server settlement and payment recovery exist, but provider-linked acceptance is not done. Quote claims precede payment-provider order creation in `functions/index.js` around lines 749–790.  
**Scenario:** Provider errors can leave a fare quote claimed; harder cases include paid order without successful fulfillment or delayed webhook replay.  
**Fix:** Operational state machine for quote/payment_attempt/booking/refund with transactional/idempotent reconciliation, job-based recovery and customer-visible retry. Test lost callback, duplicate webhook, authorization/capture delay, order generation failure, sold-out stock, concurrent checkout, refund processing and bank settlement.

**P0-05: Real driver/merchant eligibility is not operationally accepted.**  
**Files:** `src/components/DriverApp.tsx`, `src/components/MerchantPortal.tsx`, `src/components/CustomerPages.tsx`, `server/accounts.mjs`, `functions/provisionRole.js`, `functions/index.js`.  
**Evidence:** Partner application form is pending-only; verifying a driver uses stored vehicle number/license number and admin actions but there is no complete verified document upload/KYC and business license workflow. Driver transfers are recorded by operations after the external payout; automatic bank transfer is not implemented.  
**Scenario:** A nominally verified driver or merchant cannot legally/operationally fulfill jobs, or finance cannot settle an actual payout.  
**Fix:** Partner approval workflow with document storage, verification, vehicle capacity, insurance/permit fields as applicable, commercial agreement, settlement accounts, suspension, expiry alerts and auditor review; acceptance on real staging operators.

### P1 — High-priority safety, security and reliability

**P1-01: Non-geographic driver offers and assignment.**  
**Files:** `functions/index.js`, around `listDriverOffers` lines 598–610 and `acceptDriverBooking` lines 612–639; `functions/dispatchPolicy.js`.  
**Evidence:** Offer discovery fetches up to 30 matching status/service bookings without pickup proximity; acceptance enforces partner status/service/capacity but not pickup distance, freshness, route feasibility, zone or ETA.  
**Scenario:** A distant partner accepts an infeasible pickup; nearby jobs get buried among first 30.  
**Fix:** Server-owned geospatial eligibility, city/zone/geohash matching, vehicle/equipment checks, fresh-location requirement, distance/ETA ranking, offer expiry/lease, priority scoring, reoffer and fallback dispatch. Transactionally reject stale/expired offers.

**P1-02: Foreground-only driver GPS.**  
**Files:** `src/components/DriverApp.tsx`, lines 88–101; `android/app/src/main/AndroidManifest.xml`; `ios/App/App/Info.plist`.  
**Evidence:** `navigator.geolocation.watchPosition` is used while online; source comment explicitly says background updates stop. iOS declares remote notification background mode, not background location mode.  
**Scenario:** Driver locks the phone and live tracking ceases mid-delivery.  
**Fix:** Build consent-based platform-compliant background location only when required for a live job; Android foreground service/notification and correct permissions; iOS appropriate modes/purpose strings; battery optimization, stale-location UI, throttle, opt-out and privacy retention. Validate against store rules and actual devices.

**P1-03: Sensitive operations require documented custom claim reconciliation.**  
**Files:** `firestore.rules`, `functions/index.js`, `functions/operations.js`, `functions/provisionRole.js`.  
**Evidence:** Firestore `isAdmin()` trusts admin claim, while some callable admin operations additionally check database role. Some privileged functions (e.g., `processAccountDeletion` and `cancelPaidBooking`) use admin claim without equivalent role read.  
**Scenario:** Stale/erroneously provisioned claims can have disproportionate impact until token/session revocation.  
**Fix:** Central staff authorization verifying token claim, active operator account, role, permissions and optionally step-up authentication. Add staff permission matrix and revocation tests; keep least-privilege. This is a hardening concern, not evidence of an existing compromised admin.

**P1-04: Demo records are selectable inside the customer app.**  
**File:** `src/components/CustomerApp.tsx`, lines 58–77.  
**Evidence:** Fake restaurant/store/reviews and six fake `paymentStatus:'paid'` bookings appear when `import.meta.env.DEV` or `VITE_DEMO_MODE === 'true'` and live records are empty.  
**Scenario:** QA or incorrectly configured release displays fake paid orders or ratings and creates false readiness impressions.  
**Fix:** Build-time forbid demo mode in production, isolate fixture route/dev sandbox, unmistakable DEMO label, tests asserting zero production fixtures.

**P1-05: Transport custody and liability are incomplete.**  
**Files:** `src/components/TransportBookingScreen.tsx`, `functions/transportPolicy.js`, `functions/index.js` lines 640–695, `src/types.ts`.  
**Evidence:** Weight/dimensions and owner authorization are validated, plus OTP pickup and completion; no required uploaded RC/owner authorization evidence, inspection photos, condition change log, damage discrepancy review, specialized carriage options or two-person sign-off.  
**Scenario:** High-value vehicle pickup and return cannot be independently defended in a damage claim.  
**Fix:** Versioned inspection checklist, dated photos, cryptographic proof metadata, sender/receiver acknowledgment, vehicle seals/keys/fuel/odometer documents, station/leg custody events, claims and incident workflow, retention rules.

**P1-06: Money consistency must be checked at every provider boundary.**  
**Files:** `functions/index.js` payment/coupon/wallet/refund handlers, `functions/refundPolicy.js`, `functions/cartPolicy.js`, `functions/operations.js`.  
**Evidence:** Positive controls exist: server-side repricing, webhook verification, transaction-based stock and ledger updates, duplicate refund tests. There is no shown production settlement/reconciliation ledger comparing Razorpay deposits/refunds, wallet credits, merchant payable, driver payable, commission and fees.  
**Scenario:** Failed partial refunds, capture/reconciliation delays and operating commissions cannot be reliably audited with a dashboard summary.  
**Fix:** Append-only accounting events or double-entry ledger, settlement batch/reconciliation jobs, liabilities vs revenue separation, audit export, refund queues, finance alerts, tax invoices and merchant payout reconciliation.

**P1-07: Booking state model is too generic for complex logistics.**  
**Files:** `src/types.ts`, `functions/index.js`, all three booking screens.  
**Evidence:** A single enum uses `pending/accepted/preparing/ready/transit/delivered/completed/cancelled` for food, ride, parcel and vehicle transport.  
**Scenario:** Goods loading, warehouse transfer, multi-leg delivery, no-show, loss, damage, passenger pickup and return-to-sender cannot be expressed accurately or audited.  
**Fix:** Keep a shared booking aggregate but store service-specific fulfillment states, transition guards and events; explicit exception paths and compensation actions.

**P1-08: Data subject deletion can be split across stores.**  
**Files:** `server/accounts.mjs`, `server/firebaseIdentity.mjs`, `functions/index.js` lines 850–923, `src/data/neonAccounts.ts`.  
**Evidence:** Neon and Firebase each have account/deletion flows. Firebase deletion cleans selected PII, but no fully verified coordinated Neon+Firebase deletion/reconciliation exists.  
**Scenario:** Customer sees a completed deletion in one system while other data persists.  
**Fix:** One authenticated deletion request, dual-system job with checkpoints and legal retention controls, completion receipt, retries and manual exception queue; test exports and deletion on real linked profiles.

**P1-09: Frontend/backend maintainability concentration.**  
**Files:** `src/components/CustomerApp.tsx` (~112 KB), `src/components/DriverPerformanceLeaderboard.tsx` (~46 KB), `src/components/DriverApp.tsx` (~39 KB), `functions/index.js` (~92 KB), `server/accounts.mjs` (~24 KB), `src/data/firebaseHelper.ts` (~28 KB).  
**Evidence:** Very large UI/service files mix state, domain logic, access paths and view rendering; navigation is conditional in the single customer component.  
**Scenario:** A change to transport pricing breaks food checkout, global state resets incorrectly, regressions become hard to test.  
**Fix:** Feature-oriented modules and service contracts, named routes with URL/deep-link parity, typed backend adapters, independent state machines, shared design system; refactor incrementally with regression snapshots and tests.

**P1-10: Native and browser delivery needs verified builds.**  
**Files:** `android/app/build.gradle`, `ios/App/App/Info.plist`, `ios/App/App/AppDelegate.swift`, `scripts/prepare-native.mjs`, `RELEASE_HANDOFF.md`.  
**Evidence:** Android native config absent => plugin removal in development; release signing is optional unless explicit flag; iOS Xcode project exists but no signed build acceptance; Android release minification is disabled.  
**Scenario:** A distributable app may lack Google/Apple/phone auth, push, attestation or signing.  
**Fix:** Secure CI signing, mandatory release preflight, native Firebase registrations, app attestation, real hardware matrix, Play Store/App Store distribution and rollback plan. Minification is an optimization, not a substitute for protection.

### P2 — Product, UX, operations and smaller implementation issues
- `src/components/AdminDashboard.tsx` labels completed **booking value** as **Total Revenue**; this is gross merchandise/booking value, not platform revenue. Show GMV, net revenue, refunds, commission, merchant payable and driver payable separately.
- Driver registration inputs in `src/components/DriverApp.tsx` use white background and `text-white` for license/registration fields; may render unreadable text. Fix contrast and run accessibility checks.
- `src/components/OperationsConsole.tsx` accepts raw JSON for pricing configuration. Replace with schema-backed, previewable forms, role-aware approvals, versioned publishing, rollback and change history.
- `server/accounts.mjs` listens on `127.0.0.1` only. That works behind a same-host reverse proxy, but container/PaaS deployment may require a configurable host such as `0.0.0.0`; verify environment/proxy configuration before deploying.
- `PAYMENTS.md` says web payments intentionally do not work, whereas `src/payments.ts` includes Razorpay web checkout and `CustomerApp.tsx` uses it. Reconcile docs with actual product policy and provider review.
- `functions/index.js` quote is marked claimed before Razorpay order creation; a provider outage can strand a quote. Implement recovery/release and avoid charging twice.
- `src/components/CustomerApp.tsx` uses `window.alert/confirm` in checkout/error paths despite progress toward native-friendly dialogs. Replace with accessible modal/sheet feedback.
- `functions/index.js` operator-managed `operations/settlement.driverShareBps` is a single global percentage. Real products need service-specific rates, distance bonuses, tolls, waiting, cancellations, and versioned settlements.
- No `.github/workflows` paths appear in the 184-file reviewed tree. Add CI for static checks, test suites, environment guards, dependency scans, artifact builds and signed release promotion.
- `package.json` test script runs functions/server tests and secret scan; `test:rules` is separately invoked. Ensure both mandatory suites run automatically in CI.
- Verified Firestore authorization is materially stronger than early versions: default deny; customer cannot forge orders/payments or wallet balances; raw unassigned bookings are not listable by drivers; payment attempts are server-only. Continue testing negative cases, queries, legacy fields and deployed rules. The browser Firebase API key is not, by itself, a server secret.
- Legacy and current data formats need migration versioning (`driver_profiles`, customer addresses, order states, wallet balances and recipient codes).
- Add production-grade client offline state, empty/error/loading states for all modules, invalid push link handling, resuming pending checkout, contactless proof, phone interruption and low-memory recovery.

## 3. Recommended end-state architecture

### Build one platform; separate experiences and bounded domains
```

  apps/
    customer/               # web + Android/iOS Capacitor build
    driver/                 # separate branded driver shell, same shared packages
    merchant/               # merchant web/PWA and optional native shell

    public-web/             # marketing, business policies, onboarding, support
  packages/
    ui/                     # tokens, buttons, cards, forms, sheets, map controls

    auth/                   # single session model, device auth, role authorization
    maps/                   # provider interfaces, distances, geometry, address model

  backend/
```

This is a target layout, not a proposed one-shot rewrite. Use a modular monolith and maintain current deployment contracts while migrating one domain at a time. Apps may share one React codebase and packages; they should not share unrestricted role or administrative functionality. Services should communicate through typed use cases and durable events. Do **not** add microservices unless scale and team ownership justify them.

### Canonical order and financial data
- **Identity:** verified user UID; provider identities; account status; roles/permissions; partner relationships; session/device linkage.
- **Addresses:** canonical place ID, lat/lng, apartment/landmark, access instructions, contact consent, delivery zone, geocoding confidence, default address.
- **Catalog:** merchant/store, items and variants, prices in minor currency units, taxes, stock/inventory reservations, availability windows, promotion eligibility, images and business status.
- **Quotes:** persisted customer snapshot, merchant/source, destination, service option, fee/tax breakup, limits, nonce, expiry, version, eligibility, quote state.
- **Booking:** immutable accepted quote and customer/merchant/partner references; service-specific payload; payment/dispatch/fulfillment summary; optimistic version; creation/update timestamps.
- **Booking events:** append-only actor/time/location/proof/state transition. Privacy-controlled views for different roles.
- **Financial ledger:** immutable provider payment/refund IDs; credit/debit entries; commissions, taxes, merchant payables, driver payables, settlements and reconciliation status; no floating-point currency storage in accounting events.
- **Proof & disputes:** signed media references, hashes, permissions, timestamps, consents, retention periods, investigations and corrective actions.

### Key lifecycle
```
DISCOVER → DETAIL → ELIGIBILITY/COVERAGE → QUOTE → REVIEW
→ PAYMENT PENDING → PROVIDER VERIFIED → BOOKING ACCEPTED
→ PARTNER MATCHING → ASSIGNED → PICKUP/HANDOVER
→ SERVICE-SPECIFIC FULFILLMENT → PROOF → COMPLETED
→ SETTLEMENT → RECEIPT/REVIEW

Exceptions at every step:
  expiry · change of address · out of stock · no driver · reject/no-show
  loss/damage · payment interrupted · duplicate callback · partial refund
  cancellation · delayed delivery · return-to-sender · dispute
```
Every transition needs one authorized actor, permitted previous states, idempotency key, auditable event, timeout, support workflow and customer-visible status. Source of truth for payments must always be the provider-confirmed server ledger, never a screen state.

## 6. Release gates (must pass, no percent-complete guess)
**Gate A — Configuration:** independently verified staging/production projects, exact DB IDs, secrets, billing, provider URLs, webhook signing, environment guard, service pricing and legal policy URLs.  
**Gate B — Authorization:** 4+ roles, every sensitive route/collection, role revocation, linked token expiry, unassigned offers, private addresses, wallet/financial records, admin claims, abuse controls and App Check checked in emulator and staging.  
**Gate C — Money:** Razorpay signed test transactions; duplicate/delayed webhook; payment retry; no double booking; inventory concurrency; coupon concurrency; partial/full refund; wallet debt; provider-to-ledger reconciliation; real payout record.  
**Gate D — Fulfillment:** all service states and exceptions; two-party/three-party tests; real location, ETA, offline/background, chat, emergency contact, pickup/delivery proof, tracking and abandoned booking recovery.  
**Gate E — Mobile:** physical Android and iPhone device matrix, battery/location/notification permissions, app killed/reopened, cellular changes, deep links, login session restores, camera/media upload, signed builds.  
**Gate F — Operations:** staffed support, partner onboarding evidence, no-driver escalation, failed refund queues, merchant/driver payout reconciliation, backups/restore, metrics and on-call ownership.  
**Gate G — Release:** CI passing, staged deployment, canary rollout, signed store packages, verified listings and privacy disclosures, independent operator approval, rollback playbook.

## 7. Implementation sequence without destroying existing functionality
1. **Freeze baseline**: tag current `main`; snapshot migrations; enumerate canonical APIs and state transitions; add tests for every existing working flow; no big-bang rewrite.
2. **Fix environment and identity**: separate staging/production and remove ambiguous fallbacks; exercise the Neon–Firebase service identity bridge, roles and deletion.
3. **Make money and orders durable**: canonical booking events, quote-claim recovery, webhook and ledger jobs, finance dashboards and reconciliation tests.
4. **Prove first live vertical**: food delivery end-to-end with a real test restaurant, verified rider, real location, test provider payment, refund and support.
5. **Prove grocery/parcel/ride/driver-hire/vehicle transport** using independently defined completion and exception tests.
6. **Upgrade driver assignment/location and partner compliance** before increasing driver volume or geographic coverage.
7. **Refactor modules behind stable contracts**, adding automatic test coverage and deployment gates; expand to freight only after core operations are proven.
8. **Sign, test and release via staged rollout**, with monitoring, rollback and finance/on-call ownership.

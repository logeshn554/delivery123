# Owner environment setup

No live projects, payment merchant account, signed binaries or policies were created by the source remediation. Empty values represent missing owner configuration.

1. Install the Firebase CLI and authenticate the Google owner account. Create two separate Firebase projects named AllGo Staging and AllGo Production; select distinct project IDs. Enable Firestore `(default)` and the Authentication providers, register web/Android `in.allgo.app` and iOS `in.allgo.app`, and configure billing required by Functions, Maps and Secret Manager. Provider verification and billing enrollment require the owner.
2. Create distinct Neon projects/databases for staging and production under the Neon owner account. Run `node scripts/bootstrap-config.mjs`, then fill `.env.staging.local` and `.env.production.local`. These files are ignored. Never paste credentials into chat or add them to VITE variables. Startup schema creates `allgo_identity_links`; existing mappings require a reviewed unique migration before enabling the bridge.
3. Rerun bootstrap after setting actual Firebase project IDs. It prepares `functions/.env.<project-id>` without overwriting existing files. Register the matching native files locally. Each environment needs its own native registration files copied into the build workspace before sync; never check them into the repository.
4. Configure owner-controlled Razorpay test/live merchant credentials and webhook secret in each project's Secret Manager, Google Maps credentials/billing, email delivery, App Check attestation, and service account permissions for the account bridge. Accounts are hosted behind HTTPS with `ALLGO_ENVIRONMENT=staging` or `production`, `ACCOUNT_API_HOST=0.0.0.0`, exact allowed origins and a trusted reverse proxy. Avoid connecting the development database to public hosting.
5. Configure operator-owned polygons, tariffs, merchant catalogs, partner documents, privacy retention and settlement contracts. No real partners or legal prices have been invented. Verify every audit release gate and record actual evidence in `.release/<environment>.acceptance.local.json` using the example schema.
6. `node scripts/release.mjs staging deploy` checks the matching project/database, native registrations, Functions runtime and acceptance evidence before deploying. Production uses the same wrapper with `production`. Signed Android bundles use `node scripts/release.mjs production android` with the four ALLGO signing variables and Java 21. iOS requires Xcode on macOS and owner-controlled signing plus physical-device acceptance.

Demo UI is isolated: `npm run build:demo` / `npm run android:sync:demo`. Its simulated cart and order lifecycle have no account or payment API access. `npm run build` is the normal development artifact; release builds use the explicit staging/production scripts. Release Gradle tasks reject development/demo metadata, missing Firebase registration and missing signing.

Payment creation writes an intent before contacting the provider. Known rejected requests release only their own quote claim. Timeouts remain in reconciliation; the five-minute job finds the provider order by its unique receipt and reconstructs the checkout attempt. It never creates a second provider order. Unknown/duplicate matches require manual review. Receipt filtering follows [Razorpay's Orders API documentation](https://github.com/razorpay/markdown-docs/blob/master/api/orders/fetch-all.md).

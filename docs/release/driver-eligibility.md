# Driver eligibility and approval

Deploy the callable functions, client and stricter Firestore rules together. Direct client driver status/service changes and profile deletion are denied, including administrator writes. `reviewDriverEligibility` is the audited replacement; it requires current operations role plus claim, an independent operator, an existing registered driver and no unresolved active job. Decisions use a current revision and immutable request reference. Approval binds the vehicle and license details actually shown to the reviewer; conflicting profile edits require a fresh review. Decisions leave the driver offline. Rejection clears qualified services. No account role is granted by this command.

## Actual operator configuration

Before approving a driver, publish the real jurisdiction/service eligibility policy and configure `platform_config/driver_eligibility` through authorized Admin SDK infrastructure. Required fields are `enabled`, a positive integer `version`, the published HTTPS `policyUrl`, `requiredKinds` mapping each supported service to required document categories, and `expiryRequiredKinds`. Categories use the private document intake enum. Every selected service needs explicit nonempty requirements. Do not invent legal requirements or configure empty categories to bypass investigation. Advance the version whenever requirements change; policy governance, immutable version publishing and a policy editor still need implementation and acceptance.

The reviewer sees the published policy and categories and explicitly confirms the current version. The server checks the version again with the decision. Approval requires an active driver/transport application belonging to the driver; transport applications qualify only for transport. Every selected proof must belong to that same application/account and have a current clean scan, verified manual review, active retention and current expiry when required. All required categories must be present. Auth identity must have the matching application phone linked to this account's actual Firebase phone provider. Self-declared `phoneVerified` cannot satisfy this gate. Existing legacy partner approvals remain preserved and need a controlled policy-backed revalidation migration.

## Lifecycle and remaining acceptance

Eligibility state/history are source-integrated into owner-scoped account export and recursive account deletion. New decisions are blocked after account deletion begins. A real linked-provider lifecycle acceptance remains outstanding. Document audit deletion has separate retention behavior described in partner-documents.md.

This command verifies eligibility for an already provisioned driver account. Merchant role provisioning is now separately fail-closed: `functions/provisionRole.js` refuses assignment unless the catalog is bound to the account and business type and carries an approved onboarding state plus an independent, policy-versioned review and evidence references. This is an enforcement gate, not a merchant onboarding implementation; no callable currently writes that approval record. Full applicant-to-role activation, safe phone-provider linking/recovery UI, merchant/bank/tax eligibility and approval, granular staff permissions/MFA, renewal and expiry suspension, active-job suspension resolution, notification and legal/business acceptance remain incomplete. Firebase phone provider, SMS regions/quota, consent, native registrations and issuing-source checks have not been accepted in staging. Transport equipment still requires its existing specialist capability approval. Do not treat an isolated fixture identity or policy as a live provider or actual business policy.

## Idle driver document renewal

`requestPartnerRenewal` allows the approved applicant or current operations staff to reopen the same driver/transport application with a reason and expected revision. It requires that application's verified eligibility binding and an active registered driver account without a deletion request. Both the profile's custody marker and a bounded query for nonterminal assigned bookings must be clear; the driver/status index must be deployed with this change. Active jobs are retained and renewal is refused until completion or safe resolution.

Renewal atomically marks the application needs_information, makes the driver pending/offline, clears qualified services, advances eligibility/application revisions and records both histories. It preserves earned/reserved amounts and job records. The existing payout command requires verified status, so renewal temporarily prevents new payout requests too; the UI discloses this effect. Product/business acceptance must determine whether a separate verified-bank disbursement path is required during eligibility renewal. No earned funds are written off by this command.

The applicant can correct details and submit consented replacement documents through the existing intake. Scanning, independent document review and the actual current policy/phone checks remain mandatory before `reviewDriverEligibility` restores verified status; restoration keeps the driver offline until an explicit availability change. Requests are replay bound and do not grant a role. Automatic expiry escalation, safe renewal during active custody, approved-application rejection/correction variants, notifications and live journeys remain incomplete.

# Private partner documents

This is source implementation and local verification, not live onboarding acceptance. The canonical application/document workflow grants no driver, merchant or administrator access.

## Configure the actual environments

1. Create a separate private Cloud Storage bucket in each actual Firebase project. Enforce public access prevention and uniform bucket-level access; remove public IAM grants and disable object versioning, soft deletion and default/locked retention holds for this quarantine bucket. The server checks the actual bucket metadata and blocks upload, scanning, download or deletion completion if these requirements are not met. Supporting legal holds or retained object copies requires a separate explicit workflow and accepted policy. Grant the deployed Functions identity bucket-metadata read plus required object read/create/delete permissions. No live bucket or IAM policy has been created by this change.
2. Set EVIDENCE_STORAGE_BUCKET in the environment and matching functions/.env.<actual-project-id>. Run `firebase target:apply storage private-evidence ACTUAL_BUCKET --project ACTUAL_PROJECT_ID` for each real project. The release preflight checks the exact target mapping and resource separation. The release wrapper now deploys storage:private-evidence along with Functions and Firestore. The checked-in storage rules deny all client reads/writes; uploads and downloads use authenticated server commands and never create public download tokens. The target mechanism follows [Firebase's deploy target documentation](https://firebase.google.com/docs/cli/targets).
3. Publish the real document privacy policy and approve its retention period. Configure platform_config/onboarding using trusted operator tooling with evidenceEnabled:true, privacyPolicyUrl:the_actual_https_policy, retentionDays:the_actual_integer_1_to_3650. Nothing is enabled by default. Upload consent must match the policy URL and retention period shown to the applicant. A changed policy requires refresh and fresh consent.
4. Operate a private ClamAV service behind a mutual-TLS terminator. Do not expose the unauthenticated clamd TCP port to external networks. Set the daemon time zone to UTC, enable VERSION and INSTREAM, keep freshclam updates running, and enable PDF/archive scanning and alerts for encrypted content and scanning limits so an uninspected payload cannot pass as clean. Configure document/decompression/time limits and capacity for the workload. The client sends bounded INSTREAM data rather than server paths, following [the official ClamD protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html).
5. Set EVIDENCE_SCANNER_HOST and EVIDENCE_SCANNER_PORT to that verified TLS endpoint in environment and matching Functions runtime. Store EVIDENCE_SCANNER_CA, EVIDENCE_SCANNER_CLIENT_CERT and EVIDENCE_SCANNER_CLIENT_KEY in each project's Secret Manager. The TLS terminator must validate the authorized client identity; use private networking/firewall controls and certificate rotation. Client certificates, keys, CA trust and server identity need actual acceptance; no scanner, certificate or VPC was provisioned by this work.

The server uses the [Firebase Admin Storage API](https://firebase.google.com/docs/storage/admin/start) and [Cloud Storage generation preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions) for immutable creation and scoped removal. Server permissions bypass Firebase Storage rules, so IAM/public-access checks are a separate mandatory gate.

## Implemented behavior

- Only the applicant can upload against their submitted/needs-information application, with explicit consent. Supported containers are PNG/JPEG/PDF, at most 2 MiB; declared file type must match its container signature. These checks do not establish image validity, malware safety or document authenticity.
- Reservations are durable and replay bound to content hash, category, label, application, owner and declared expiry. Limits are ten active documents per application and twenty per account, including documents attached to older applications. Concurrent uploads share transactional quota records.
- Objects are immutable, private and quarantined. A failed/uncertain storage request can be retried with the same reference; the applicant can select Resume original upload after a restart and provide the same original bytes. Changed content cannot reuse it. Expired reservations or changed privacy policy cannot be resumed. Deletion or account deletion begun during upload invalidates finalization and removes late-created bytes.
- The scanner checks the stored generation, byte length, CRC and SHA-256 before sending content over mutual TLS. It rejects signature databases older than 48 hours or with an invalid/future time. A clean scan moves a file to ready_review; infected files cannot be downloaded and become due for deletion. Scan failures remain quarantined, with a rotating cursor for retries. Clean does not mean identity/KYB verified.
- Download requires current applicant ownership or actual administrator role plus claim, a clean scan, matching bytes/generation, an unexpired retention period and an account without an owner deletion request. Access and retention are rechecked before the audit record and response. Scans older than seven days are requeued before download. No persistent bearer download URL is issued.
- The hourly retention worker pages through expired metadata and removes actual objects before publishing deletion. Failed deletions remain pending and rotate for retry. Manual deletion clears document-specific scan/download audit records and decrements quotas once. Account deletion invokes the same object cleanup and removes the account's quota record. Bucket soft-deleted/versioned copies and provider backups require a separately accepted lifecycle/retention policy.
- Applicants and operators can page through private metadata. Native save/share uses the official Filesystem and Share plugins; web uses a temporary browser download. Native copies stay in the app's private cache for the receiving share app, then are removed by a one-hour timer or expired-copy cleanup at a later app startup/export. User-selected destination copies are outside AllGo's control. Force-kill/background timing must be accepted on real devices.
- Account exports include application history and document metadata. Scanned document files can be retrieved separately from the application. Large, asynchronous exports remain unfinished.

## Acceptance required before enabling real document collection

Verify unauthorized/anonymous/forged-admin reads and writes on the deployed bucket and metadata; confirm no public grants, tokens, object versions or undeclared retained copies. Test valid files, MIME mismatch, over-limit uploads, quota races, interrupted uploads, concurrent removal and dual-provider account deletion against staging. Use an actual clean document and the official EICAR test file against the real scanner; verify infected/encrypted/limit-exceeded/stale-signature/TLS-certificate-error cases cannot reach review/download. Verify hash/generation mismatch, permissions revoked during retrieval, expired retention retries and audit cleanup. Establish scanner health/backlog, stale signatures, retention failure and IAM-change alerts with operator response ownership.

Build/sign/test Android and iOS on physical devices, including file chooser permissions, share/save cancellation and completion, force-kill cleanup, cold/warm links, resumed sessions, keyboard and safe-area behavior. iOS requires CocoaPods/Xcode on macOS; sync on Windows does not compile iOS. Complete document review, verified expiry, reapplication, legal/business identity checks, ownership/role assignment, business activation, staff permissions and historical application migration. Those workflows are still unfinished.
## Audited manual document review

Verified operations staff retrieve a clean, current file through the private download command before recording its decision. The download receipt binds reviewer, generation, hash and review revision. `reviewPartnerEvidence` requires independent reviewers, an open application, active retention, a scan within seven days and retrieval within 24 hours. Verification requires an issuing-source case reference and explicit authenticity/expiry checks; expiry dates are checked in UTC and may be corrected separately from the applicant's declaration. Feedback is applicant-visible; source references stay in the restricted evidence audit. Decisions are revision checked and replay safe; competing reviews must retrieve again. Deleting the document removes its review/access audit with it.

This records an operator's actual investigation; it does not automate government identity verification or prove an issuing source was contacted. A clean malware scan does not establish document authenticity. No decision grants a role, activates a business or overrides the complete operating-eligibility review. Acceptance still requires actual authorized reviewers, jurisdiction-specific evidence requirements, real issuing-source verification, notification/escalation for expiry, phone verification, bank/tax review and an audited activation/suspension workflow. Those gates remain unfinished.

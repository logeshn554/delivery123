# Order notifications

Customer, merchant and delivery app registrations include their audience alongside platform and token. The audience selects notification routing; it does not grant account permissions. Partner registration requires the current assigned merchant role or verified driver profile. Tokens are server-only records keyed by token hash and expire after 90 days.

Booking changes notify the customer app, the currently assigned verified driver's delivery app, and merchant apps whose current account is assigned to the matching restaurant/grocery business. Disabled/suspended accounts, revoked partner roles, preference opt-outs, expired tokens and malformed expirations are excluded. The trigger reads the current booking before selecting recipients so delayed events do not deliberately route to historical assignees. Authorization is rechecked on all subsequent order reads/actions; a push payload grants no access.

When a paid or COD booking becomes dispatchable and remains unassigned, a separate generic offer alert is sent to online, verified, location-consented drivers whose approved service, pickup-zone coverage, fresh location, vehicle/equipment and pickup distance match. The payload contains only the opaque booking ID, trigger event ID and `dispatch_offer` type. It includes no customer, contact, address, price or parcel details. Tapping it opens the driver's offer workspace, which reloads through the guarded callable; `acceptDriverBooking` rechecks eligibility and the lease transactionally. This alert complements foreground polling and is not a reservation or proof of assignment.

The visible message is generic and includes no contact, address, amount or order status. Its data contains a booking identifier and event identifier. Permanent invalid-token responses delete the registration. Transient failures leave it for trigger retry; retries can send duplicates and exactly-once delivery is not claimed.

Legacy registrations without an audience retain customer routing. Legacy partner devices must enable notifications again in their matching app, which updates the registration. Merchant and driver workspaces expose an opt-in button; Android/iOS Firebase registration and permission are prerequisites. Customer preferences continue to control order updates for the whole account.

Order-update taps resolve the pending booking identifier only against the current authorized booking feed. Merchant routing requires both assigned business and catalog type; assigned-driver routing requires current assignment. A dispatch-offer tap opens the driver's current offer workspace without attempting a direct booking read. The order-update notice receives focus and announces the current status. Active merchant requests focus the matching order controls, and active driver requests select the corresponding job; terminal updates remain informational. Requests wait up to 15 seconds for the feed before showing a generic unavailable state. Dismissal restores normal browsing. A supplied identifier never initiates a direct privileged booking fetch. Removed assignments immediately stop displaying resolved details.

Manual Neon logout and API-detected account expiry share native cleanup: invalidate pending push intent, drain already-started token/registration work, disable push refresh opt-in, clear pending booking navigation, stop local driver location, attempt remote consent withdrawal and device unregister, delete the native push token, and sign out native Firebase before removing primary credentials. Pending permission dialogs are invalidated without waiting for user interaction; their late completion cannot register or restore opt-in. Expired remote authorization does not prevent later local cleanup. Concurrent account teardown calls share one operation; replacement login waits before its network request and credential acceptance. Firebase-only manual logout uses the same device cleanup. These are best-effort operations: remote cleanup may fail after expiry or offline, and plugin failures are isolated.

Registration and refresh capture the current Firebase user object and local push generation, and recheck after asynchronous permission/token/registration results. Opt-in records its owner UID locally; startup and refresh require that UID to match the current account. Legacy flags without an owner and flags belonging to another UID do not auto-register: enable notifications explicitly from the current account. This local ownership marker is not authorization; the callable still verifies the current identity, partner role and audience.

Provider/device acceptance remains required: register each native app with Firebase, verify permission denial/recovery, foreground/background/killed-app delivery, token refresh, account switch/logout/expiry including pending permission/token/registration work, correct workspace after tapping, and recipient changes. Dispatch alerts depend on a current eligible driver at the booking trigger; later drivers still rely on foreground polling. Guaranteed offline logout revocation, expiry detection without an account API response, plugin-failure recovery and duplicate suppression remain unfinished. A hanging SDK operation can delay the drain; real provider timing and process death require device acceptance. No real push or provider call is made by the isolated integration tests.
